# المعمارية العامة

## 1. النمط المعماري: Modular Monolith

مع نطاق المشروع الحالي (شركة واحدة، عدة مستودعات، فريق تطوير صغير)، أنسب نمط
هو **Modular Monolith**: تطبيق واحد، لكن مقسّم داخليًا لوحدات مستقلة منطقيًا:

- `identity` — المستخدمون، الأدوار، الصلاحيات لكل مستودع
- `org` — المستودعات/الفروع والمواقع الداخلية (Zones/Bins)
- `catalog` — الأصناف، التصنيفات، الوحدات
- `inventory` — الأرصدة، حركات المخزون، الدفعات، الجرد، التحويلات
- `purchasing` — الموردين، أوامر الشراء، الاستلام
- `sales` — العملاء، أوامر البيع، إذون الصرف
- `reporting` — التقارير والتنبيهات

الفائدة: سرعة تطوير أعلى من Microservices (لا حاجة لإدارة شبكة/نشر معقد)، مع
حدود واضحة بين الوحدات تسهّل تقسيم أي وحدة لخدمة مستقلة لاحقًا لو كبر النظام
(مثلاً فصل `reporting` في خدمة تحليلات منفصلة).

## 2. الـ Stack المقترح

| الطبقة | الاختيار | السبب |
|---|---|---|
| **Frontend + Backend** | Next.js (App Router) + TypeScript | نفس نمط المشروع الآخر بالريبو (`web/`)، Server Actions تغني عن API منفصل في المرحلة الأولى، ونقدر نفصل Backend مستقل لاحقًا لو احتجنا عميل تاني (موبايل native، تكامل خارجي) |
| **قاعدة البيانات** | PostgreSQL | التزام ACID قوي ضروري لحركات مخزون مالية حساسة (لازم نضمن عدم فقد أي حركة أو تعارض أرصدة عند عمليات متزامنة) |
| **ORM** | Prisma | Type-safety كامل مع TypeScript، Migrations واضحة، ونفس الأداة المستخدمة في المشروع الآخر بالحساب |
| **المصادقة (Auth)** | جلسات JWT موقّعة + RBAC | نفس نمط `web/` (JWT بدون خدمة خارجية)، مع طبقة صلاحيات إضافية "الدور داخل كل مستودع" (نفس المستخدم ممكن يكون مدير في فرع ومشاهد بس في فرع تاني) |
| **الباركود** | قراءة بالكاميرا من المتصفح (`getUserMedia` + مكتبة زي `@zxing/browser`) | بما إن المنصة "ويب فقط"، مفيش حاجة لتطبيق موبايل مخصص أو جهاز قارئ منفصل — أي جهاز فيه كاميرا (تابلت/موبايل/لابتوب) يكفي |
| **التخزين المؤقت (لاحقًا)** | Redis | لتسريع لوحة التحكم (KPIs) وقائمة انتظار للتنبيهات، غير ضروري في MVP |
| **التحديث اللحظي (لاحقًا)** | WebSocket / Server-Sent Events | لعرض تغيّر الأرصدة لحظيًا لو أكتر من مستخدم بيشتغل على نفس المستودع في نفس الوقت |
| **الاستضافة** | أي مزود Node.js + PostgreSQL مُدار (Neon / Supabase / Render) | نفس نمط `web/` الموجود بالفعل بالريبو |

## 3. مخطط المكوّنات (نصّي)

```
المتصفح (أمين مخزن / مدير فرع / أدمن)
        │  HTTPS
        ▼
Next.js App (App Router)
 ├─ صفحات الواجهة: Dashboard / Inventory / Purchasing / Sales / Reports / Admin
 ├─ Server Actions + Route Handlers → منطق الأعمال لكل وحدة (Module)
 ├─ Middleware: تحقق الجلسة (JWT) + التحقق من الصلاحية حسب (المستخدم + المستودع)
 └─ Prisma Client
         │
         ▼
   PostgreSQL (سكيمة متعددة المستودعات، انظر database-schema.md)
```

عناصر تُضاف لاحقًا عند الحاجة فعليًا (وليس من اليوم الأول): Redis للتخزين
المؤقت، Object Storage لصور الأصناف والمرفقات، طابور رسائل (Queue) للتنبيهات
والبريد الإلكتروني.

## 4. مبدأ أساسي: الـ Ledger هو مصدر الحقيقة

أهم قرار معماري في نظام مخزون: **لا نعدّل الرصيد الحالي مباشرة أبدًا**. كل
عملية (إدخال، صرف، تحويل، تسوية جرد) تُسجَّل كصف جديد في جدول `StockMovement`
(سجل تاريخي لا يُعدَّل ولا يُحذف)، والرصيد الحالي (`StockBalance`) هو **قيمة
مُشتقة** تتحدث تلقائيًا من مجموع الحركات. هذا يضمن:

- تتبّع كامل (Audit Trail) لأي فرق في الرصيد ومين عمله وإمتى.
- إمكانية إعادة حساب الأرصدة من الصفر في أي وقت للتأكد من عدم وجود خطأ.
- تفادي تعارض التحديثات المتزامنة (عدة مستخدمين بيسجّلوا حركات في نفس اللحظة).

تفاصيل الجداول في [`database-schema.md`](database-schema.md).
